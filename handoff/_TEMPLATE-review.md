# 審查：review-<proj>-<slug>

> 由 `review-rd` 填寫。唯讀審查，**不替人改程式**。

| 項目 | 內容 |
|------|------|
| 審查對象 | `handoff/<proj>-rd-<slug>.md` |
| 專案 | `<專案名>` |
| 分支 | `<branch>` |
| 審查輪次 | 第 N 輪 |
| 結論 | 通過 / 需修正 |
| 審查時間 | `YYYY-MM-DD HH:MM` |

## 審查依據

| 來源 | 內容 |
|------|------|
| handoff | 宣稱改了什麼 |
| `git -C <cwd> status --short` | 實際動到的檔案 |
| `git -C <cwd> diff` | 實際差異 |
| 專案規範 | role 檔「專案硬規範」與 PROJECTS.md 的規範庫 |

**handoff 與實際 diff 不一致要明寫**（漏報檔案、多改檔案都算 Major 以上）。

## Blocker

會導致功能錯誤、資料錯誤、安全問題，或違反專案硬規範。必須修。

- `path/to/File:123` — 問題描述 + 為什麼是 Blocker

## Major

不會立刻壞，但違反架構慣例、遺漏錯誤處理、效能風險。應修。

- `path/to/File:45` —

## Minor

命名、註解、格式、可讀性。可修。

- `path/to/File:88` —

## 通過項

確認沒問題的部分，寫出來讓 lead 知道審過了哪些。

- 

## 未能審查的部分

缺乏資訊、需要執行環境才能判斷的，老實列出。

- 例：實際效能無法靜態判斷，建議上線前實測
